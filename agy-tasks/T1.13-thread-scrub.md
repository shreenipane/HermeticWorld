## Part A: revision as of `T_world` (mutable-content rule)
- Fetch the target issue's **edit history** through the GitHub GraphQL API (`POST https://api.github.com/graphql`; the query asks for the issue's `body`, `createdAt`, `lastEditedAt` and `userContentEdits(first: 100)` with `createdAt`, `editedAt`, `diff`; follow `pageInfo` cursors). Add a `http_post_json` alongside `make_http_get` with the same caching and token handling (cache key = SHA-256 of URL + body). GraphQL needs a token: when none is configured, fall back to the current behaviour and keep the warning.
- `userContentEdits` lists **full revisions**, newest first (its `diff` field holds the body text of that revision in practice; treat it as the revision text and document the assumption with a link-free note). The body **as of `T_world`** is the newest revision with `editedAt <= T_world`; if none qualifies and the issue was created at or before `T_world`, the original body (the oldest revision); and per §4, when `T_world` is **earlier than the issue's creation**, take the **first revision** (the original body).
- If the issue body was never edited (`lastEditedAt` null), the scraped body is already the revision as of `T_world`: no change, no warning.
- Replace the problem statement's issue-body part with that revision. SWE-bench's `problem_statement` is "title + body" of the issue(s); keep the title as scraped (titles have their own edit history; record a warning `title taken as scraped` only if `TitleEdit`-type history is found, which you may skip implementing: just record that titles are not revision-checked).
- Apply the same rule to **hints**: SWE-bench `hints_text` is made of issue comments created before the fix PR's first commit. Fetch the issue's comments with their edit histories (GraphQL `comments(first: 100) { nodes { createdAt, body, lastEditedAt, userContentEdits(...) } }`), keep only comments **created at or before `T_world`** (stricter than SWE-bench's definition, per the thread scrub) and take each at its revision as of `T_world`. Write the result to `staging/hints.txt` in the same format the current code uses.
- Record in the task's intake metadata: `problem_statement_revision` (`as_scraped` | `revision_at_t_world` | `first_revision`), the chosen revision's `editedAt`, the number of edits ignored, and `hints_revisioned: true/false`.

## Part B: target-thread scrub list
Produce `staging/thread_scrub.json`: everything the world must not serve for this task, independent of dates:
- the target issue's discussion **after the problem statement**: every comment on the target issue created after `T_world` (by ID and HTML URL);
- the **solution PR** (its HTML URL, API URL, `/files`, `/commits`, `.diff` and `.patch` URLs) and all its review comments and reviews (IDs and URLs);
- every issue or PR that **links to the target** (GraphQL `timelineItems(itemTypes: [CROSS_REFERENCED_EVENT, CONNECTED_EVENT])` on the target issue, plus the existing `linked_refs` parser applied the other way where cheap) with their URLs;
- each entry: `{kind, url, reason}`; sorted, de-duplicated. Also add URL **prefixes** for the solution PR (`https://github.com/<repo>/pull/<n>`) so any sub-page is covered.
This file is data for later layers (WorldServer, web archive): nothing consumes it yet; document its schema in the module docstring.

## Tests (offline, with fixtures)
- Body edited after T_world (fix pasted in later): the problem statement uses the earlier revision; the fix text is absent; metadata says `revision_at_t_world`.
- T_world before issue creation: first revision used, metadata `first_revision`.
- Never-edited body: unchanged, no warning.
- No token: falls back to as-scraped with the existing warning, no GraphQL call made.
- Hints: a comment created after T_world is dropped; an earlier comment edited after T_world is taken at its earlier revision.
- Pagination of edits and comments (two pages).
- Thread scrub: the PR, its review comments, a cross-referencing issue and a late comment all appear with reasons; output is sorted and stable across runs.
- Malformed or partial GraphQL responses (missing fields, errors array): a clear error or a warning with fallback, never a crash; a GraphQL `errors` response is never cached.
