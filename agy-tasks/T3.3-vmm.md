# Task T3.3: `hermetic-vmm`, Firecracker + jailer orchestration (TR-VMM-1, TR-VMM-2, TR-VMM-5; TR-VMM-6 reserved slots only)

You are the coding agent on Hermetic World (it seals benchmark worlds so that no post-cutoff or host information leaks to an agent). In Phase 3 containers are replaced by Firecracker microVMs: AgentVM, NetVM, ExtractorVM and GraderVM. `hermetic-vmm` is the host-side library that prepares, starts, configures and destroys those VMs. A mistake here leaks the host (date, identity, network) into the guest or lets a hostile guest disk hurt the host.

Read first: `HERMETIC_WORLD_ARCHITECTURE.md` §3 (overview, rings), §7.1, §8.1, §8.2 (all of it), §9.4, §9.5, §11.4, Appendix A; `TRD.md` §4.7 (TR-VMM-1 to TR-VMM-6) and TR-SEC-*; `agy-tasks/T3.1-execd.md` and `agy-tasks/T3.2-guest-kernel.md` (the guest side and boot arguments this crate must produce); `crates/hermetic-world-server` (crate layout, error style, how it refuses unsafe directories and symlinks); `crates/hermetic-common/src/world_manifest.rs`.

## Crate

Also add at the repository root: `vmm/hide-kvmclock.cpu-template.json` (Firecracker custom CPU template, x86_64, that clears bits 0 and 3 of CPUID leaf `0x40000001` register eax and changes nothing else) and `vmm/firecracker.lock.json` (pinned Firecracker version, release URL, and sha256 fields set to the literal `"TO-BE-FILLED-BY-OWNER"`; never invent a hash).

## What to build
1. **VM specification.** Typed `VmSpec`: role (Agent, Net, Extractor, Grader), vCPUs, memory, kernel image path, boot arguments, root drive (read-only), further drives with explicit read-only flags, reserved empty drive slots (TR-VMM-6: a slot for the tests disk that can be attached later with `PATCH /drives`), vsock (guest CID, Unix socket path), network interfaces (tap name, guest MAC), CPU template path, clock level (`faked` only in this task; `hidden` is refused with an error that names the unmet TR-VMM-3 requirements). Strict validation with named caps before anything touches the filesystem: per-role rules (AgentVM: no network interface except the one to NetVM, root drive read-only, overlay drive read-write; ExtractorVM and GraderVM: no network at all), MACs are fixed project-assigned values derived deterministically from role and index (never host-derived, never random), guest CIDs ≥ 3 and unique in a run, boot arguments must pass the same required/forbidden rules as T3.2 (implement the rule table in Rust here: required `clocksource=tsc`, `tsc=reliable`, `hermetic.t=`, `ro`; forbidden `rw`, `ip=`, any other `clocksource=`).
2. **Firecracker configuration (TR-VMM-2, TR-VMM-5).** A pure function from a validated `VmSpec` to the ordered list of API requests (method, path, JSON body): machine config, CPU template (always applied), boot source, drives, vsock, network, entropy device (virtio-rng always attached), and **never** an MMDS request, never a balloon, never a metrics/logger path outside the jail. Known-answer tests with full expected JSON for an AgentVM and an ExtractorVM; a test that no produced request path starts with `/mmds` for any role; a test that the CPU template file in `vmm/` parses and modifies exactly leaf `0x40000001` eax bits 0 and 3.
3. **Jail plan.** A pure function producing the jailer argument vector and the jail directory layout for a VM id: dedicated uid/gid per VM taken from a configured range (never the caller's uid), chroot base, cgroup v2 settings (cpu, memory, pids caps from the spec), network namespace name, `--new-pid-ns`, resource limits (file size, open files). Files enter the jail by hard link or copy decided by a documented rule; guest-writable disks are never hard-linked from a shared original. VM ids are validated (charset, length) because they become path components. Known-answer test of the argument vector. Running the jailer needs root: provide the real runner behind a trait and an `#[ignore]` integration test that explains what it needs; all logic is tested through a fake runner.
4. **Lifecycle.** `Vmm` with `prepare`, `start`, `wait_ready`, `pause`, `resume`, `stop` (graceful through execd is the caller's job; this crate sends the API action and then enforces a hard kill deadline), `destroy` (removes the jail directory through held directory descriptors, never following symlinks, refusing if the directory identity changed). Every step has a deadline; a VM that does not come up is destroyed and the error says which step failed. Process handling: the Firecracker child is started with a cleared environment (explicit allow-list), closed inherited descriptors, its own process group, and stdout/stderr captured with a size cap. On drop, a running VM is killed. State machine is explicit; invalid transitions are errors (tested).
5. **API client robustness.** Tests run the client against a fake Firecracker (a Unix-socket server inside the test) that: answers correctly; returns 400 with a fault body; sends an oversized body; sends a truncated response; stalls forever (the deadline must fire); closes early. None may panic, hang or allocate from an untrusted length.
6. **Host paths.** Kernel, rootfs and overlay images are opened once, checked to be regular files owned by the caller or root and not writable by group/others (same rule as the WorldServer's directory checks), and passed on by descriptor or by jail-relative path; no check-then-use by path; symlinked components are refused.
7. **Unjailed development mode.** For hosts without root, a clearly named `DevUnjailed` runner starts Firecracker directly (no jailer) so that the in-VM integration test can run with `/dev/kvm` access only. It must be impossible to select from a production run configuration (compile-time feature `dev-unjailed`, off by default; a test asserts the default build refuses it). Add an `#[ignore]` integration test `boots_guest_and_reads_guest_clock` that, given `HERMETIC_FC_BIN`, `HERMETIC_KERNEL` and `HERMETIC_ROOTFS` in the environment, boots a VM with `hermetic.t=` and checks over vsock that execd answers a status request and reports guest time equal to T_clock within a tolerance; it must skip with a clear message when any variable is missing.
8. **`plan` subcommand**: reads a VmSpec JSON (size-capped, deny unknown fields) and prints the API request list and jail plan as deterministic JSON; exit 0 ok, 2 refused by validation, 1 error.
9. **Docs** `crates/hermetic-vmm/README.md`: roles and their rules, the request order, what `faked` means and why `hidden` is refused for now, how to fill `vmm/firecracker.lock.json`, how to run the ignored tests.
