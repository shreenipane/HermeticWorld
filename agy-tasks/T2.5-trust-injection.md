# Task T2.5: per-world CA and trust-store injection (TR-SEAL-10)

You are the coding agent on Hermetic World. NetVM terminates TLS for the sealed world with leaf certificates signed by **one CA per world version**. Every client in the rootfs must trust that CA, and the CA must be **deterministic**: TR-SEAL-12 requires that sealing the same task twice gives an identical `world_root`, so the CA certificate bytes must be identical on every build of the same world.

Read first: `HERMETIC_WORLD_ARCHITECTURE.md` §7.2 (TLS and trust stores) and §13.1 (the Network group: CA certificate digest, trust-store paths); `TRD.md` TR-SEAL-10 and TR-SEAL-12.

## Design decisions (already made; follow them)
- **Key:** RSA-2048, generated deterministically: `seed = HKDF-SHA256(ikm = 32-byte host secret from --ca-seed-file, salt = "hermetic-world-ca-v1", info = world_id)`, then `ChaCha20Rng::from_seed(seed)` drives RSA key generation. RSA because PKCS#1 v1.5 SHA-256 signatures are deterministic and every client, including 2019-era OpenSSL 1.0.2/1.1.0 in old conda envs, accepts RSA roots.
- **Certificate:** X.509 v3, subject and issuer `CN=Hermetic World CA <first 16 hex of BLAKE3(world_id)>, O=Hermetic World`, serial = first 16 bytes of SHA-256(`"serial:" + world_id`) with the top bit cleared, validity `T_clock − 10 years` to `T_clock + 10 years` (whole seconds, UTC; compute from `T_clock`, never from the host clock), basicConstraints CA:true critical, keyUsage keyCertSign + cRLSign critical, subjectKeyIdentifier. Signature RSA PKCS#1 v1.5 SHA-256.
- **Leaves** (library function for NetVM later): `mint_leaf(ca, hostnames, t_clock)` → leaf for the given DNS names, validity `T_clock − 7 days` to `T_clock + 365 days`, its own deterministic RSA key from `HKDF(ca seed, info = "leaf:" + sorted hostnames)`.
- The **private key never goes into the rootfs.** It is written only where `--key-out` says, mode 0600.

## CLI
- `hermetic-trust mint-ca --world-id ID --t-clock RFC3339 --ca-seed-file FILE --cert-out CA.pem --key-out CA.key` (refuses a seed file that is not exactly 32 bytes or is group/world readable).
- `hermetic-trust install --rootfs DIR --ca-cert CA.pem [--report OUT.json]`: install the CA into every trust store found under the rootfs staging directory (never the host's):
  1. **System bundles:** `etc/ssl/certs/ca-certificates.crt` (Debian/Ubuntu/Alpine), `etc/pki/tls/certs/ca-bundle.crt` and `etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem` (RHEL family), `etc/ssl/cert.pem`; also drop the PEM at `usr/local/share/ca-certificates/hermetic-world-ca.crt` and `etc/pki/ca-trust/source/anchors/hermetic-world-ca.pem` when those directories exist.
  2. Every `certifi/cacert.pem` and every conda `ssl/cacert.pem` anywhere in the tree (walk without following symlinks; a symlinked bundle is resolved **inside the rootfs** as if the rootfs were `/`, and the target file is updated once).
  3. **Java keystores** named `cacerts`: if the file is a JKS keystore (magic `0xFEEDFEED`), add a trusted-certificate entry with alias `hermetic-world-ca` and rewrite the keystore integrity hash with the default password `changeit` (implement the small JKS format: version 2, entries, SHA-1 over password-as-UTF-16BE + "Mighty Aphrodite" + data). If it is PKCS#12, do not modify it; list it in the report as `unsupported_pkcs12` so a later task can handle it.
  4. Appending is idempotent: a bundle that already holds this exact certificate is not changed. Preserve file modes and ownership; write atomically (temp file plus rename in the same directory).
  - The report JSON lists `ca_cert_sha256`, every modified path (rootfs-relative), skipped paths with reasons, and the environment defaults for the run spec: `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `PIP_CERT`, `NODE_EXTRA_CA_CERTS`, `GIT_SSL_CAINFO`, `CARGO_HTTP_CAINFO`, all pointing at the system bundle path that exists in this rootfs.

## Tests (offline)
- **Determinism:** minting twice with the same seed, world id and T_clock gives byte-identical certificate PEM; a different world id or seed gives a different certificate.
- Validity window equals T_clock ± 10 years exactly; it does not depend on the host clock (mint with a T_clock in 2019 and in 2023).
- With `openssl` available: `openssl x509 -noout -text` parses the CA and shows CA:TRUE; `openssl verify -CAfile ca.pem leaf.pem` succeeds for a minted leaf, with `-attime` set inside the leaf window and fails outside it.
- Install into a fake rootfs with a Debian bundle, a RHEL bundle, two certifi bundles (one symlinked absolutely, e.g. `/usr/lib/python3/dist-packages/certifi/cacert.pem` → `/etc/ssl/certs/ca-certificates.crt`, which must resolve inside the rootfs), a conda bundle, a JKS `cacerts` built in the test, and a PKCS#12-looking `cacerts`: every bundle gains the CA once, a second install changes nothing, the JKS round-trips (parse it back, check the alias and the integrity hash), PKCS#12 is reported unsupported, and nothing outside the rootfs is touched.
- Hostile inputs: a truncated JKS, a JKS with a huge entry count, a bundle that is a directory, a symlink loop: errors or skips with reasons, no panic.
- The private key file has mode 0600 and never appears under the rootfs.
